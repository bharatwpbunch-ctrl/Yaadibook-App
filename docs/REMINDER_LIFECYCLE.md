# Yaadibook — Reminder Lifecycle & State Transitions

## 1. Lifecycle Overview

Reminders follow an explicit, deterministic state machine. They can be created manually or auto-generated by recurring business engines (maintenance occurrences or AMC renewals).

```
   [ Create / Reconcile ]
             │
             ▼
       ┌───────────┐
       │  pending  │◄─────────────┐
       └─────┬─────┘              │
             │                    │
      ┌──────┴──────┐             │ (Snooze time elapsed)
      │             │             │
      ▼             ▼             │
┌───────────┐ ┌───────────┐       │
│ completed │ │  snoozed  │───────┘
└───────────┘ └─────┬─────┘
                    │
                    ▼
              ┌───────────┐
              │ cancelled │
              └───────────┘
```

---

## 2. State Descriptions

| Status | Meaning | Conditions / Effective Status |
|---|---|---|
| `pending` | Active task awaiting action. | If `due_at < now()`, effective status is **Overdue**. If `due_at` is today, effective status is **Due Today**. Otherwise **Upcoming**. |
| `snoozed` | Temporarily deferred. | Has `snoozed_until` set in the future. Once `snoozed_until <= now()`, it automatically behaves as active/due. Original due date is preserved in `original_due_at`. |
| `completed` | The business task has been finished. | Has `completed_at` timestamp, optional `completed_notes`, and `completed_by_user_id`. Never marked overdue. |
| `cancelled` | The reminder is discarded. | No longer surfaces in active views or notification dispatch. |

## 3. Snoozing Workflow

Yaadibook offers quick 1-tap snoozing options tailored for mobile business owners on the move:
1. **Later Today (+3 hours)**: Postpones the alert by 3 hours from current time.
2. **Tomorrow Morning (9:00 AM)**: Snoozes until 09:00:00 IST the following day.
3. **In 3 Days (9:00 AM)**: Postpones until 3 days ahead.
4. **Next Week (9:00 AM)**: Postpones by 7 days.
5. **Custom Date & Time**: Full calendar and time picker.

### Stored Procedure: `public.snooze_reminder`
```sql
CREATE OR REPLACE FUNCTION public.snooze_reminder(
    p_reminder_id UUID,
    p_snooze_until TIMESTAMPTZ
)
RETURNS public.reminders
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
    v_reminder public.reminders;
BEGIN
    SELECT * INTO v_reminder FROM public.reminders WHERE id = p_reminder_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'Reminder not found';
    END IF;

    UPDATE public.reminders
    SET status = 'snoozed',
        original_due_at = COALESCE(original_due_at, due_at),
        snoozed_until = p_snooze_until,
        due_at = p_snooze_until,
        updated_at = timezone('utc', now())
    WHERE id = p_reminder_id
    RETURNING * INTO v_reminder;

    RETURN v_reminder;
END;
$$;
```

## 4. Completion Workflow

When an owner marks a reminder complete:
- Optional completion notes can be captured (e.g., "Customer confirmed visit next Monday").
- Timestamp `completed_at` is recorded in UTC.
- Any undelivered items in `notification_queue` for this reminder are marked as cancelled to prevent phantom alerts.

### Stored Procedure: `public.complete_reminder`
```sql
CREATE OR REPLACE FUNCTION public.complete_reminder(
    p_reminder_id UUID,
    p_notes TEXT DEFAULT NULL
)
RETURNS public.reminders
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
    v_reminder public.reminders;
BEGIN
    SELECT * INTO v_reminder FROM public.reminders WHERE id = p_reminder_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'Reminder not found';
    END IF;

    UPDATE public.reminders
    SET status = 'completed',
        completed_at = timezone('utc', now()),
        completed_by_user_id = auth.uid(),
        completed_notes = p_notes,
        updated_at = timezone('utc', now())
    WHERE id = p_reminder_id
    RETURNING * INTO v_reminder;

    -- Cancel any pending notification queue items for this reminder
    UPDATE public.notification_queue
    SET status = 'cancelled',
        updated_at = timezone('utc', now())
    WHERE reminder_id = p_reminder_id AND status = 'queued';

    RETURN v_reminder;
END;
$$;
```

## 5. Idempotent Reconciliation

To prevent duplicate reminders when maintenance plans or AMC contracts are modified, the system uses idempotent reconciliation procedures:
- `reconcile_maintenance_occurrence_reminder`: Uses unique composite key `(business_id, source_type, source_id)` where `source_type = 'maintenance_occurrence'`.
- `reconcile_amc_contract_reminders`: Uses unique key `(business_id, source_type, source_id)` where `source_type = 'amc_contract'`.

If the source occurrence is rescheduled, the linked reminder's `due_at` is automatically updated without creating duplicates or clearing owner notes.
